AI RESEARCH AGENT — TECHNICAL DOCUMENTATION

1. OVERVIEW

The AI Research Agent is an intelligent software system designed to answer questions, perform research, use external tools, maintain conversation context, and retrieve information from private documents.

The system consists of a React frontend, a Python FastAPI backend, an AI agent powered by a large language model, a collection of tools, a planning component, a memory component, and a retrieval system.

The primary objective of the project is to understand how modern AI agents work internally rather than relying completely on high-level frameworks.

The agent receives a question from the user and determines what actions are required to answer it. Depending on the question, the agent can perform calculations, search the web, retrieve information from documents, or use previous conversation context.


2. SYSTEM ARCHITECTURE

The frontend is developed using React and communicates with the backend through HTTP requests.

The backend is developed using Python and FastAPI. FastAPI provides API endpoints that receive questions from the frontend and return responses generated by the AI agent.

The AI agent communicates with a large language model through an API. The model is responsible for understanding the user's request, deciding whether a tool is necessary, and generating the final response.

3. LARGE LANGUAGE MODEL

A large language model, commonly called an LLM, is a machine learning model trained on large amounts of text.

The LLM is responsible for understanding natural language and generating responses. However, an LLM by itself does not automatically have access to every external system.

For example, an LLM cannot automatically access a private company database, execute arbitrary Python functions, or search a website unless an application provides the required capability.

The AI Research Agent solves this problem by connecting the LLM with external tools.

The LLM decides what should happen, while the Python application executes the requested operation.


4. TOOL CALLING

Tool calling allows an LLM to request that an external function be executed.

A calculator tool can perform arithmetic operations such as addition, subtraction, multiplication, and division.

For example, when the user asks:

"What is 25 multiplied by 4?"

the model can request the calculator tool.

The Python application receives the tool request and executes the calculator function.

The calculator returns 100.

The result is then sent back to the LLM.

The LLM can use the result to produce the final answer.

This creates the following process:

User question
|
LLM
|
Tool request
|
Python function
|
Tool result
|
LLM
|
Final answer


5. CALCULATOR TOOL

The calculator tool performs basic mathematical operations.

Supported operations include:

Addition
Subtraction
Multiplication
Division

For addition, the tool receives two numbers and returns their sum.

For subtraction, the tool subtracts the second number from the first number.

For multiplication, the tool multiplies the two numbers.

For division, the tool divides the first number by the second number.

The calculator should handle division by zero safely instead of allowing the application to crash.

Using a calculator tool is useful because it separates deterministic computation from language generation.


6. WEB SEARCH TOOL

The web search tool allows the agent to retrieve information from the internet.

Web search is useful when the user asks about current events, recent technology releases, current companies, recent research, or other information that may change over time.

The search tool receives a natural-language query.

For example:

"latest AI developments in 2026"

The search system returns information such as titles, URLs, and summaries.

The agent can then use these results when generating the final response.

A search tool should not be treated as permanent knowledge. Search results represent information retrieved at a particular time.


7. AGENT LOOP

The agent loop is one of the most important parts of an AI agent.

The basic process is:

1. Receive the user question.
2. Send the question to the LLM.
3. Check whether the LLM requested a tool.
4. Execute the requested tool.
5. Return the tool result to the LLM.
6. Allow the LLM to decide what to do next.
7. Continue until the LLM produces a final answer.

This process can contain multiple iterations.

For example:

User:
Calculate 20 multiplied by 5 and then add 10.

The agent may first call:

calculator(20, 5, multiply)

The result is:

100

The agent can then call:

calculator(100, 10, add)

The result is:

110

The agent finally returns 110 to the user.

This behavior is called tool chaining because the result of one tool call becomes an input to another operation.


8. PLANNING

Planning allows the agent to break a complex question into smaller research tasks.

For example, a user may ask:

"Compare OpenAI, Google, and Anthropic."

Instead of attempting to answer everything in one step, the planner can create several tasks.

Task 1:
Research OpenAI.

Task 2:
Research Google.

Task 3:
Research Anthropic.

The agent can execute each task separately and then combine the results.

Planning is particularly useful for research questions because complex questions often contain multiple independent subtasks.

The planner in this project uses an LLM to generate a structured list of tasks.


9. CONVERSATION MEMORY

Conversation memory allows the agent to use information from previous interactions.

For example:

User:
What is Python?

Agent:
Python is a programming language.

User:
Who created it?

The word "it" refers to Python because the previous conversation provides the context.

Without conversation memory, the second question may be ambiguous.

Short-term conversation memory can be stored in a Python list while the application is running.

Persistent memory can be stored in an external file or database.

The current learning implementation initially uses a JSON file to demonstrate persistence.

In a production system, a database such as PostgreSQL can be used instead.


10. PERSISTENT MEMORY

Persistent memory means that information remains available even after the application is restarted.

A Python list stored in RAM disappears when the application stops.

A JSON file can preserve the information on disk.

A database can provide a more robust persistent storage mechanism.

A production memory system may store:

User messages
Assistant responses
Conversation identifiers
Timestamps
User preferences
Important facts
Agent state

Persistent memory should be designed carefully because storing every message forever can increase storage requirements and can also increase the amount of context sent to the LLM.


11. RETRIEVAL-AUGMENTED GENERATION

Retrieval-Augmented Generation is commonly abbreviated as RAG.

RAG allows an AI system to retrieve relevant information from an external knowledge source before generating an answer.

The basic RAG process is:

User question
|
Retriever
|
Relevant information
|
LLM
|
Answer

For example, suppose a company document contains:

"Employees receive 25 days of annual leave."

A user asks:

"How many annual leave days do employees receive?"

The retrieval system searches the company's documents and finds the relevant statement.

The retrieved information is then provided to the LLM.

The LLM generates an answer based on the retrieved information.

RAG is useful because the information does not have to be contained in the original training data of the LLM.


12. WHY RAG IS IMPORTANT

RAG is useful for private or specialized information.

Examples include:

Company policies
University documents
Technical documentation
Legal contracts
Research papers
Product manuals
Internal knowledge bases
Customer support documents

Instead of retraining an LLM every time a document changes, a retrieval system can retrieve the latest relevant information.

This makes RAG more flexible for knowledge that changes frequently.


13. BASIC RETRIEVAL

A simple retrieval system can search documents using keywords.

For example, if the user asks:

"What is RAG?"

the system can look for paragraphs containing words related to the question.

Keyword retrieval is easy to implement but has limitations.

A user may ask:

"How does the system obtain information from private documents?"

The document may discuss "retrieval" without using the exact phrase "obtain information."

A simple keyword system may fail to recognize that these concepts are related.


14. EMBEDDINGS

Embeddings solve some of the limitations of keyword matching.

An embedding converts text into a numerical vector.

Texts with similar meanings tend to have vectors that are closer together in vector space.

For example:

"What is RAG?"

and:

"Explain retrieval augmented generation."

have different words but similar meanings.

An embedding model can represent both sentences as vectors that are semantically similar.

The retrieval system can compare the vector of a user's question with vectors stored for document chunks.


15. VECTOR DATABASE

A vector database stores embeddings and allows similarity searches.

The typical RAG pipeline is:

Document
|
Split into chunks
|
Embedding model
|
Vectors
|
Vector database

When a user asks a question:

Question
|
Embedding model
|
Query vector
|
Vector database
|
Most similar chunks
|
LLM
|
Answer

Examples of technologies that can be used for vector storage include PostgreSQL with pgvector and specialized vector databases.


16. DOCUMENT CHUNKING

Large documents are usually divided into smaller pieces called chunks before generating embeddings.

Chunking is important because sending an entire large document to an LLM for every question is inefficient.

For example, a 100-page document can be divided into many smaller sections.

Each section can be embedded independently.

When the user asks a question, the retrieval system can return only the most relevant sections.

Good chunking improves retrieval quality.

Chunks that are too small may lose important context.

Chunks that are too large may contain too much unrelated information.


17. RAG AND MEMORY

RAG and conversation memory solve different problems.

Conversation memory stores information about previous interactions with the user.

RAG retrieves information from external knowledge sources.

For example:

Memory:
"The user previously asked about Python."

RAG:
"The company documentation states that Python is used for backend services."

An AI agent can use both systems at the same time.


18. MCP

MCP stands for Model Context Protocol.

MCP is a protocol designed to standardize how AI applications connect to external tools and data sources.

An MCP server can expose tools or resources to an AI application.

Examples of capabilities could include:

Database access
File access
GitHub operations
Search
Calendar operations
Company APIs

The AI model can decide when a capability is needed.

The MCP layer provides a standardized way for applications to discover and use those capabilities.


19. MCP COMPONENTS

An MCP architecture commonly involves:

MCP Host
MCP Client
MCP Server

The host is the AI application.

The client maintains the connection to an MCP server.

The MCP server exposes capabilities such as tools and resources.

A simplified architecture is:

AI Application
|
MCP Client
|
MCP Server
|
+-------------+
|             |
Tools       Resources


20. FUNCTION CALLING VS MCP

Function calling and MCP are related but different concepts.

Function calling allows an LLM to request execution of a specific function.

MCP provides a standardized protocol for connecting AI applications to external capabilities.

For example, an application can directly define a calculator function using a function-calling API.

With MCP, the calculator capability could instead be exposed by an MCP server.

Function calling is about the model requesting an action.

MCP is about standardizing the connection between AI applications and external capabilities.


21. DATABASE

A database provides structured persistent storage.

PostgreSQL is a relational database system that can store information using tables and relationships.

The AI Research Agent can eventually use PostgreSQL to store:

Users
Conversations
Messages
Research tasks
Documents
Document chunks
Embeddings
Tool execution logs

PostgreSQL can also be extended with pgvector for vector similarity search.

This makes PostgreSQL a possible foundation for both normal application data and vector-based RAG.

23. SECURITY

AI agents must be designed with security in mind.

External tools should validate their inputs.

Database queries should use parameterized statements.

API keys should never be placed directly in frontend code.

Sensitive credentials should be stored in environment variables or a secure secrets manager.

Web search results should not automatically be trusted as authoritative.

Tools should have limited permissions.

The agent should not be allowed to perform dangerous operations without appropriate authorization.


24. EVALUATION

An AI agent should be evaluated rather than judged only by whether individual examples appear correct.

Useful evaluation categories include:

Answer accuracy
Tool selection accuracy
Retrieval accuracy
Planning quality
Latency
Token usage
Failure rate
Hallucination rate

Example evaluation:

Question:
What is RAG?

Expected behavior:
Retrieve the relevant RAG information and produce an accurate answer.

Observed behavior:
The system retrieves unrelated information.

This indicates a retrieval problem rather than necessarily an LLM generation problem.


25. FUTURE IMPROVEMENTS

Future versions of the AI Research Agent can include semantic vector retrieval, PostgreSQL persistence, MCP-based tools, authentication, multi-agent workflows, streaming responses, better document processing, evaluation pipelines, caching, and production deployment.

A more advanced architecture can contain specialized agents.

For example:

Research Agent
Planning Agent
Retrieval Agent
Tool Agent
Synthesis Agent

Each component can have a specific responsibility.

However, a multi-agent architecture should only be introduced when it provides a real advantage. A well-designed single agent is often simpler and easier to debug.

The goal of the project is to understand the fundamental mechanisms behind AI agents before introducing advanced frameworks.
