AI Research Agent — Technical Documentation
1. Overview
The AI Research Agent is an intelligent software system designed to answer questions, perform research, use external tools, maintain conversation context, and retrieve information from private documents.
The project is designed to demonstrate the fundamental mechanisms behind modern AI agents before introducing advanced frameworks.
2. System Architecture
The basic architecture consists of a React frontend, a FastAPI backend, an AI agent powered by an LLM, external tools, retrieval-augmented generation, and persistent memory.
The frontend sends a user's question to the FastAPI backend. The agent interprets the request and can use tools, retrieve information from documents, access conversation memory, and synthesize a final response.
A simplified architecture is:
User → React UI → FastAPI → AI Agent → Tools / RAG / Memory
3. Large Language Model
The Large Language Model acts as the reasoning and language generation component of the agent.
The model can understand natural-language questions, decide when a capability is needed, request tool calls, interpret tool results, and generate a final response.
4. Tool Calling
Tool calling allows the AI model to request external functions when it needs capabilities that are not directly available through text generation.
Examples of tools include:
•	Calculator
•	Time
•	Web Search
The AI model can decide when a capability is needed.
5. Calculator Tool
The calculator tool performs basic arithmetic operations such as addition, subtraction, multiplication, and division.
Using a dedicated calculator prevents the agent from relying on the language model to perform arithmetic itself.
6. Time Tool
The time tool provides the current date and time.
This allows the agent to obtain dynamic time information instead of relying on information contained in the model's training data.
7. Web Search Tool
The web search tool allows the agent to search the internet for external or current information.
The agent can use web search when a question requires information that may have changed or is not contained in its internal knowledge.
8. Agent Loop
The agent loop allows the model to repeatedly interact with tools until it has enough information to answer the user's request.
A simplified loop is:
User Question → LLM → Tool Call → Tool Result → LLM → Final Answer
This is different from a single LLM request because the agent can perform multiple actions before producing the final response.
9. Planning
A planning component can break a complex user request into smaller research tasks.
For example, a request to compare multiple technologies can be divided into separate tasks for researching each technology followed by a synthesis step.
The Planning Agent creates a set of research tasks and the agent executes those tasks before producing the final answer.
10. Conversation Memory
Conversation memory allows the agent to maintain context across multiple questions.
For example, if a user asks about Python and then asks about its benefits, the agent can use the previous conversation to understand that "its" refers to Python.
The current implementation stores recent conversation messages.
11. Persistent Memory
Persistent memory allows conversation information to survive application restarts.
The project currently uses a JSON file as a simple learning implementation for persistent conversation storage.
A production implementation can replace this file-based storage with PostgreSQL or another database.
12. Retrieval-Augmented Generation
Retrieval-Augmented Generation (RAG) is a technique where an AI system retrieves relevant information from external documents before generating an answer.
RAG allows the model to use information from private or specialized documents instead of relying only on information encoded in the model.
A basic RAG pipeline consists of:
Document → Chunking → Embeddings → Vector Store → Retrieval → LLM
13. Why RAG Is Important
Language models may not have access to private company documents, project documentation, internal knowledge bases, or newly created information.
RAG provides a mechanism for supplying relevant external information to the model at query time.
This can improve factual grounding and allow the system to answer questions using a controlled knowledge source.
14. Document Processing
Before documents can be searched semantically, they are divided into smaller sections called chunks.
Chunks should be small enough for efficient retrieval while containing enough context to represent a meaningful piece of information.
The current learning implementation initially uses paragraphs as document units.
15. Embeddings
An embedding converts text into a numerical vector that represents semantic information.
For example, two sentences with similar meanings can have vectors that are close to each other even when they use different words.
The project uses a Sentence Transformer model to generate embeddings.
The current test model is:
all-MiniLM-L6-v2
This model produces 384-dimensional embeddings.
16. Semantic Retrieval
Semantic retrieval compares the embedding of a user's query with embeddings of document chunks.
Cosine similarity can be used to measure how similar two vectors are.
The retrieval process is:
User Query → Query Embedding → Similarity Calculation → Top Relevant Chunks
This is more powerful than simple keyword matching because semantic similarity can identify related concepts even when the exact words are different.
17. Vector Database
A vector database stores document embeddings and allows efficient similarity search.
For a small learning project, embeddings can temporarily be kept in memory.
For a production system, a vector database or PostgreSQL with pgvector can be used.
18. RAG and Memory
RAG and conversation memory solve different problems.
Memory stores information about previous interactions with the user.
RAG retrieves information from external documents.
Memory answers questions such as:
"What were we discussing earlier?"
RAG answers questions such as:
"What does this project documentation say about RAG?"
A complete agent can use both mechanisms together.
19. MCP
The Model Context Protocol (MCP) is a standardized way for AI applications to discover and use external capabilities.
The MCP layer provides a standardized connection between AI applications and external capabilities.
The host is the AI application.
Examples of possible MCP capabilities include:
•	Search
•	Calendar operations
•	Company APIs
•	Database operations
20. Function Calling vs MCP
Function calling is about the model requesting an action.
MCP is about standardizing the connection between AI applications and external capabilities.
Function calling can be implemented directly inside an application.
MCP provides a more standardized architecture for exposing tools and resources to AI applications.
21. Database
A database provides structured persistent storage.
PostgreSQL is a relational database system that can store information using tables and relationships.
A database can store:
•	Users
•	Conversations
•	Messages
•	Documents
•	Metadata
•	Application state
PostgreSQL can also serve as a foundation for vector-based RAG when combined with pgvector.
22. Production Architecture
A production version of the AI Research Agent can contain:
•	React frontend
•	FastAPI backend
•	Agent orchestration
•	LLM provider
•	Tool layer
•	MCP servers
•	PostgreSQL
•	Vector search
•	Authentication
•	Logging
•	Monitoring
•	Evaluation
The database stores persistent application data.
23. Security
AI agents should follow the principle of least privilege.
Tools should have limited permissions.
External APIs should use secure authentication mechanisms.
API keys and secrets should be stored in environment variables rather than source code.
User data should be protected through appropriate authentication, authorization, and access controls.
24. Multi-Agent Architecture
A more advanced architecture can divide responsibilities among specialized agents.
Example:
Research Agent
Planning Agent
Retrieval Agent
Tool Agent
Synthesis Agent
However, a multi-agent architecture should only be introduced when it provides a real advantage. A well-designed single agent is often simpler and easier to debug.
25. Evaluation
AI agents should be evaluated systematically.
Important evaluation areas include:
•	Answer correctness
•	Tool selection
•	Retrieval quality
•	Grounding
•	Latency
•	Cost
•	Reliability
•	Safety
Evaluation datasets can contain representative questions and expected outcomes.
26. Future Improvements
Future versions of the AI Research Agent can include semantic vector retrieval, PostgreSQL persistence, MCP-based tools, authentication, multi-agent workflows, streaming responses, better document processing, evaluation pipelines, caching, and production deployment.
27. Project Goal
The goal of the project is to understand the fundamental mechanisms behind AI agents before introducing advanced frameworks.
The project progressively demonstrates:
LLM → Tool Calling → Agent Loop → Planning → Memory → RAG → MCP → Database → Production
